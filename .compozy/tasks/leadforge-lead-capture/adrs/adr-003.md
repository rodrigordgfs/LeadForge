# ADR-003: TypeScript Monorepo with BullMQ Job Pipeline

## Status

Accepted

## Date

2026-06-11

## Context

LeadForge is a greenfield SaaS with no existing codebase. The PRD requires an asynchronous pipeline (search → analyze → score → conditional artifact generation) with user-facing SLAs (60s basic results, 2min scores, 5min full artifacts). Playwright workers for Google Maps mining run natively in Node.js. The team chose a single-language stack to minimize operational complexity for MVP.

## Decision

Adopt a **TypeScript monorepo** (pnpm workspaces) with:

- **`apps/web`** — Next.js 15 App Router (UI + Route Handlers for REST/SSE)
- **`apps/worker`** — BullMQ job processors (Playwright scraping, site analysis, artifact generation)
- **`packages/db`** — Prisma ORM + PostgreSQL schema
- **`packages/shared`** — Domain types, segment catalog, score rules, job payloads
- **`packages/queue`** — BullMQ queue definitions and job type enums

Job pipeline orchestrated via **BullMQ on Redis** with three primary queues: `search`, `analyze`, `artifacts`.

## Alternatives Considered

### Alternative 1: Go API + Node Playwright Workers

- **Description**: Go REST API with separate Node worker service communicating via Redis.
- **Pros**: Go performance for API; Playwright stays in Node.
- **Cons**: Two languages, duplicated types, slower MVP velocity, polyglot debugging.
- **Why rejected**: Greenfield MVP benefits from shared TypeScript types across web, API, and workers.

### Alternative 2: Python FastAPI + Playwright

- **Description**: Python backend with Playwright Python bindings.
- **Pros**: Playwright has Python support; FastAPI is mature.
- **Cons**: Separate frontend repo; weaker type sharing with Next.js; team chose TS monorepo.
- **Why rejected**: User selected TypeScript monorepo option.

## Consequences

### Positive

- End-to-end type safety from job payloads to API responses.
- Playwright runs in the same language/runtime as workers.
- Single toolchain (pnpm, Vitest, ESLint) across all packages.
- Next.js Route Handlers avoid a separate API deployment for MVP.

### Negative

- Node.js API less performant than Go for high-concurrency edge cases (acceptable for MVP).
- Worker and web share deployment concerns if not containerized separately.

### Risks

- **Monorepo complexity**: Mitigate with clear package boundaries and Turborepo task caching.
- **Long-running jobs blocking web process**: Mitigate by running workers in separate `apps/worker` process/container.

## Implementation Notes

- Docker Compose: `postgres`, `redis`, `web`, `worker`.
- Environment variables shared via `.env` with `packages/shared` validation (Zod).
- Clerk auth middleware on all API routes except health check.
