# ADR-005: Artifact Storage as Base64 in PostgreSQL

## Status

Accepted

## Date

2026-06-11

## Context

Generated artifacts include PDFs (proposal, diagnosis, wireframe) and structured TXT files. Object storage (S3/R2) is the typical pattern for binary files, but the product owner chose to store artifacts as **base64-encoded content directly in PostgreSQL** for MVP simplicity.

## Decision

Store all generated artifacts in a PostgreSQL `artifacts` table:

```sql
artifacts (
  id, lead_id, type, filename, mime_type,
  content_base64 TEXT,  -- base64-encoded file content
  size_bytes, created_at
)
```

Types: `company_txt`, `analysis_txt`, `website_brief_txt`, `proposal_pdf`, `diagnosis_pdf`, `wireframe_pdf`.

API serves artifacts by decoding base64 on download. No S3/R2/MinIO in MVP.

## Alternatives Considered

### Alternative 1: Cloudflare R2 / AWS S3

- **Description**: Store files in object storage; DB holds URL/key only.
- **Pros**: Scalable, cheap at volume, keeps DB lean.
- **Cons**: Extra infrastructure, signed URL logic, local dev complexity.
- **Why rejected**: User chose base64 in database for MVP.

### Alternative 2: Local Filesystem

- **Description**: Write files to disk; store path in DB.
- **Cons**: Not portable across containers/replicas; breaks on serverless.
- **Why rejected**: User chose database storage.

## Consequences

### Positive

- Single data store — no object storage setup for MVP.
- Simple backup/restore (PostgreSQL dump includes artifacts).
- Straightforward LGPD deletion (cascade delete with lead).

### Negative

- Database bloat: a 3-PDF package (~1–3 MB) × many leads increases table size quickly.
- Base64 encoding adds ~33% storage overhead.
- Serving large PDFs through API adds memory pressure on decode.
- Not suitable beyond moderate artifact volume without migration.

### Risks

- **DB size growth**: Mitigate with Phase 2 migration path to object storage documented in TechSpec; monitor `artifacts.size_bytes` aggregate.
- **Performance**: Mitigate with streaming decode, pagination, artifact size cap (5 MB per file).
- **Connection pool exhaustion on large downloads**: Mitigate with direct bytea column option in Phase 2 (more efficient than TEXT base64).

## Implementation Notes

- Max artifact size: 5 MB raw (reject larger in worker).
- Index on `(lead_id, type)` for fast lookup.
- Migration note in TechSpec Phase 2: move to R2 with `storage_key` column, keep base64 path as fallback.
